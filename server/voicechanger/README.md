# Realtime RVC voice conversion (w-okada/voice-changer)

Lucy 2.5 is a **video** model — it produces the live avatar image and no voice at
all. The audio that goes out with that avatar during a call is the live audio
already paired with the avatar pipeline (the microphone track the app streams up
as outgoing call audio). This directory wires that live stream through
[w-okada/voice-changer](https://github.com/w-okada/voice-changer) running RVC,
continuously and in real time.

```
Lucy 2.5 live video (unchanged)  ──────────────────────────────► outgoing video
                                                                 (Telegram pipe)
live audio paired with the avatar pipeline
        │  (browser → /api/social-call/media, channel 0x02)
        ▼
w-okada/voice-changer · RVC  (server/voice_changer.mjs drives it)
        │  16 kHz mono int16, chunk in → chunk out, never batched into
        │  sentences, never written to a file
        ▼
converted voice
        ├─ Telegram  → /tmp/tgcalls_audio.pcm  (the audio track that travels
        │                                       with the Lucy video)
        └─ WhatsApp  → back to the browser (channel 0x04) → swapped in as the
                       outgoing WebRTC audio track of the Green API call
```

What is **not** happening anywhere in this path: no prerecorded audio, no
file round-trip, no TTS, no LLM, no waiting for a pause or a complete
sentence. Audio in → audio out, chunk after chunk, for the whole call.

## Install

```bash
bash server/voicechanger/setup.sh     # clone + venv + torch/onnxruntime
bash server/voicechanger/start.sh     # or VOICE_CHANGER_AUTOSTART=1
```

`setup.sh` never runs automatically and never fails the deployment — it is a
multi-gigabyte install and the rest of the app must deploy regardless.

Everything is installed **outside** this repo, under `$VOICE_CHANGER_HOME`
(default `~/voice-changer`), so nothing heavy is committed.

## Load an RVC model

voice-changer only converts through a model loaded into a numbered *slot*.
Two ways to fill one:

**Its own WebUI** (handy for browsing/testing): start the server, open
`http://<host>:18888`, upload the `.pth` (+ optional `.index`).

**This app's API** (scriptable, no browser needed):

```bash
curl -X POST https://<backend>/api/social-call/voice/load-model \
  -H 'Content-Type: application/json' \
  -d '{"slot":0,"pthPath":"/path/to/your/model.pth","indexPath":"/path/to/your/model.index"}'
```

That uses voice-changer's documented upload → concat → `load_model` flow, so
the slot metadata (embedder, f0, sampling rate, embChannels…) is generated by
voice-changer itself from the checkpoint rather than guessed.

Then pick the slot, either in the call-prep screen or by setting
`VOICE_CHANGER_MODEL_SLOT=0` on the backend.

## Backend environment variables

| Variable | Default | Meaning |
| --- | --- | --- |
| `VOICE_CHANGER_URL` | `http://127.0.0.1:18888` | Where the VCClient server listens. Point this at another host to run conversion off-box. |
| `VOICE_CHANGER_MODEL_SLOT` | `-1` | Slot to convert with. `-1` = no model, audio passes through untouched (and the UI says so). |
| `VOICE_CHANGER_AUTOSTART` | `0` | `1` = let `server.mjs` launch/respawn `start.sh`. |
| `VOICE_CHANGER_SAMPLE_RATE` | `16000` | Conversion I/O rate. 16 kHz matches both RVC's internal processing rate and the Telegram call audio pipe, so no resampling happens. |
| `VOICE_CHANGER_CHUNK_MS` | `32` | Target size of one conversion request. Smaller = lower latency, more CPU per second. |
| `VOICE_CHANGER_MAX_QUEUE_MS` | `240` | Hard cap on queued audio. Exceeding it drops the **oldest** samples, so latency can never creep up unnoticed. |
| `VOICE_CHANGER_CROSSFADE_SAMPLES` | `512` | voice-changer `crossFadeOverlapSize` (SOLA crossfade, in samples at 16 kHz). |
| `VOICE_CHANGER_EXTRA_SAMPLES` | `1024` | voice-changer `extraConvertSize` — how much past audio each inference looks at. Raising it can stabilise pitch at the cost of latency. |
| `VOICE_CHANGER_TRAN` | model default | Pitch shift in semitones (RVC `tran`). |
| `VOICE_CHANGER_INDEX_RATIO` | model default | Feature-retrieval ratio (RVC `indexRatio`), 0–1. |
| `VOICE_CHANGER_PROTECT` | model default | Consonant/breath protection (RVC `protect`), 0–0.5. |
| `VOICE_CHANGER_F0_DETECTOR` | model default | `rmvpe_onnx` (default), `harvest`, `dio`, `crepe_onnx_full`… `dio` is the lightest on CPU. |
| `VOICE_CHANGER_TIMEOUT_MS` | `5000` | If VCClient stops answering mid-call, fall back to pass-through after this long instead of freezing the outgoing audio. |

## Latency expectations

Conversion adds roughly *one chunk of capture + one inference + one chunk of
playout*, plus network. The browser sends 16 kHz chunks (32 ms by default),
one request is in flight at a time, and samples that arrive while a request is
out are coalesced into the next one — so on a slow machine the chunks grow
instead of the delay growing.

`GET /api/social-call/voice/status` reports `stats.inferenceMs` (what
voice-changer said each conversion cost) and `stats.queuedMs` (how much audio
is waiting). If `queuedMs` sits well above zero, this host cannot keep up with
the chunk size — raise `VOICE_CHANGER_CHUNK_MS`, switch to a lighter
`VOICE_CHANGER_F0_DETECTOR`, or move conversion to a GPU host.

## Failure behaviour (no silent pretending)

* VCClient not running / unreachable → audio is forwarded **unchanged**, status
  reports `mode:"bypass"` plus the reason, and the UI shows “not converting”.
* No model slot selected → voice-changer is put in its own pass-through mode so
  the call keeps its real voice rather than going silent.
* VCClient stops answering mid-call → same bypass, and it reconnects and
  re-applies the configuration by itself once it comes back.

Incoming caller audio is never touched by any of this.
